# Proposal Assistant / مساعد العروض — concept, not implemented

Status: reviewed product/technical plan only. RASED remains at version 0.2.6; no AI feature implementation, installer, release, or provider account has been created. Gemini is the **only provider for the first implementation**. Keep it separate from the pending notification-priority change until the user reviews this plan and requests implementation.

## What the feature should do

From a project's detail page, the user chooses **Prepare proposal**. RASED gathers the currently stored title, full public description when available, skills, category and budget. It combines these with the user's own editable profile (real experience, skills, portfolio links, usual tone) and optional project-specific price/time notes. The user reviews the exact information to be sent and presses **Generate**. The model returns an editable draft, a short list of assumptions/missing information, and possibly questions worth asking the client. The user edits and copies the proposal, then opens Mostaql to submit manually. No automatic bidding, login, browser session access, or background AI generation.

The first version is *context-guided LLM drafting*, not RAG. Retrieval-augmented generation becomes meaningful when the user adds a portfolio or successful previous proposals: select only the most relevant user-owned snippets for the current project. Start with local keyword/full-text ranking; add embeddings only if actual retrieval quality calls for them. Never imply that all historical projects should be uploaded or indexed by a cloud service.

## Existing data and gaps

`src/shared/types.ts` already exposes `ProjectFull` and `ProjectDetails`. `src/renderer/views/ProjectDetailView.tsx` displays full description when fetched, otherwise the RSS excerpt, with provenance indicating full/truncated/excerpt. `src/main/details.ts` fetches and caches full details on demand with a budget and retry logic. The generation flow should request details through this existing path, show when full text is unavailable or truncated, and never pretend an excerpt is the complete project. The current personal note is not automatically part of the prompt; obtain explicit consent for that field.

## Proposed flow and architecture

1. **Onboarding in Settings → AI / Proposal Assistant:** show Gemini as the fixed first provider, let the user enter their own Gemini API key, and set language, tone, real skills and portfolio examples. Show that API usage may cost money and that project text/profile content will leave the device only when the user presses Generate. Offer a delete-key action and local-only profile reset. Candidate default model: Google's current stable `gemini-3.8-flash` for new projects; recheck model availability and pricing before implementation and pin an exact model ID. Do not silently switch models on users.
2. **Secret handling:** renderer sends the key once through a narrow validated IPC call; Electron main stores only encrypted bytes via Windows DPAPI-backed `safeStorage`, outside SQLite settings, exports, logs and Git. Main never returns the full key to renderer. Require OS encryption availability; fail closed rather than plaintext fallback. Handle key rotation, provider rejection, password change and deletion. This protects against another Windows user, not malware running under the same user account.
3. **Generation:** renderer requests a draft for one project ID. Main resolves the project from its own DB, checks description provenance, includes only fields approved in the preview, and calls Google's Gemini API over HTTPS. Main owns `AbortController`, timeout, retry-after/rate-limit handling and per-request output limits. Keep a small provider adapter interface (`generateProposal` and typed error/result), with only one Gemini implementation; no provider picker, fake adapters or speculative dependencies in v1. One explicit click produces one API call; no calls from the RSS watcher or Windows notifications.
4. **Prompt boundary:** label client project text as untrusted data. Treat requests inside that text to ignore instructions, leak secrets or take actions as data, not instructions. Tell the model to use only supplied facts about the freelancer, avoid invented experience/portfolio/guarantees, address the client's concrete requirements, and flag missing price or delivery time rather than guessing. A bounded response can contain `{proposal, assumptions, questions}`. The app validates length and strips dangerous markup; it never executes model output.
5. **Review:** show an editable Arabic/English draft, quick regenerate/refine options only on explicit paid clicks, copy action, and project link. Keep drafts locally in SQLite only when the user chooses Save or through a clearly explained local autosave. The user is responsible for checking accuracy and submitting on Mostaql.
6. **Privacy and documentation:** update the in-app privacy statement, generated privacy/terms files and README before release. The 2026-09-28 legal text already discloses Gemini as a **future optional feature**, not a current network flow. At implementation, verify that descriptions exactly match actual request fields and secret handling; remove “future/not available” wording only when the feature is shipped. Explain free-tier versus paid-service processing and any changes in Google terms at release time. Do not claim that “local app” means “no data leaves the device” after enabling AI. Review Mostaql's current terms and provider terms before publishing; public project visibility alone does not grant broad rights to redistribute project text.

## Gemini-first provider contract and data choices

- Use a key created by each user in Google AI Studio, never a key bundled with the open-source executable. Do not ask the user to paste their secret into GitHub, a chat, a screenshot or a test fixture. New AI Studio keys may be authorization keys; use Google's supported API/SDK authentication, not assumptions about key prefixes. Old unrestricted standard keys may be rejected by Gemini.
- Google warns against exposing keys in client-side apps. RASED is a distributed local desktop app, so no shared developer key can be secured inside it. Windows DPAPI-backed `safeStorage` reduces at-rest exposure for each user's own key, but cannot defend against same-user malware or a modified app. A backend proxy would be needed to protect a developer-owned shared key; RASED has no such backend.
- Prompt preview must name every field sent to Google. Default: selected project's title, text (full/truncated/excerpt with label), skills, category and budget plus the user-approved skills/profile snippets. The personal note, project URL, other projects, RSS feed history, diagnostics, Google account data and unrelated drafts are excluded by default. No automatic attachments, grounding, Google Search or Maps in MVP.
- Google terms say unpaid Gemini API inputs/outputs may be used to improve services and reviewed by humans; sensitive/confidential/personal data should not be sent to unpaid services. Paid services tied to active billing are not used for product improvement but can be logged for abuse monitoring. The desktop app should not infer service tier merely from a key. Present this warning before first generation, link the current official terms, and let users decide what they are authorized to send. Check eligibility/age/region and any EEA/UK/Swiss paid-only restriction before distribution.
- Google's available-regions list currently includes Egypt, but availability still depends on the user's account, age, network location and future policy changes. Verify account-level access during implementation; do not treat this list as a universal guarantee.
- No RAG/embeddings in the first implementation. If later adding retrieval, index only user-provided or user-authorized portfolio material locally and display the snippets selected for a prompt. Keep the Gemini provider adapter independent of the retriever so additional providers can be added without database migration.

## UX details that matter

- The entry point belongs on each project detail page; a dedicated Assistant page can hold profile, drafts and history. Avoid making users copy project text manually.
- Show **Full description / Truncated / RSS excerpt only** before generation. Let users paste missing details themselves if needed.
- Require user-provided facts for portfolio, price, delivery schedule and availability. Highlight blanks and unsupported claims in the draft.
- Keep proposal style concise and human. A useful draft mentions the client's specific need, a relevant proof point, an approach, realistic delivery and one focused question. Repeated generic introductions are a poor product outcome.
- Show provider/model and a rough usage indicator before each call, then actual token/cost data when the provider returns it. Do not present a fixed cost when model pricing can change.
- Preserve unsaved edits while navigating; never overwrite a modified draft silently. Provide clear errors for missing key, invalid key, quota, rate limit, network timeout and provider downtime.

## Acceptance checks before release

- Main process never logs/exports/returns the plaintext key; encrypted storage survives app restart and can be deleted. Invalid key and unavailable encryption fail safely.
- Generating from full detail and excerpt-only projects labels provenance accurately; one click makes at most one request under normal conditions and Cancel stops it.
- A malicious instruction embedded in project text cannot change provider destination, expose key, navigate windows or trigger extra tools/calls. Output is editable text, not executable HTML.
- No AI call occurs during RSS polling, notifications, startup or opening a project. No automated proposal submission.
- Draft/assumptions fields remain accurate under missing budget, missing client requirements and truncated detail. User can edit/copy/save without losing work.
- Tests use a local mocked Gemini adapter and a fake key; never consume a real quota in CI. Manual checks cover real Gemini auth/key types, available fixed model ID, free/paid warning, billing indicators, Arabic draft quality and the updated privacy notice.

## Inputs needed from the project owner before implementation

1. Confirm that Gemini's current terms and direct transmission of selected project text to Google are acceptable for the intended audience. Free-tier handling is materially different from paid.
2. Provide **non-secret** example profile data: real skills, 2–3 portfolio descriptions/links that you are authorized to use, preferred Arabic/English proposal voice, and typical quote/delivery assumptions. These can be entered into the app later instead of sent in chat; no personal API key is needed in this planning stage.
3. Choose whether MVP should save generated drafts automatically on-device or only after pressing Save. Default proposal: autosave locally, with a Delete drafts action and an explicit note that drafts remain in the unencrypted application database.
