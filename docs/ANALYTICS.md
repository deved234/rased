# Usage analytics

## Required acceptance (0.10.0 and later)

Since 0.10.0 the official configured distribution implements the owner's explicit **accept or exit** requirement. Before feature views mount or any platform polling starts, the user sees bilingual disclosure and must press **Agree & use RASED**, or exit. Updates alone never authorize capture. The disclosure is `2026-10-21-v4`; earlier enabled participants need renewed acceptance. Previous declines remain disabled and now encounter the explicit access requirement instead of being silently enabled. Withdrawing stops collection and monitoring and returns to this screen; local data and deletion-support controls remain available. Existing source pause, disable and backoff choices are preserved. A provider/network outage after acceptance does not lock the app; the bounded local queue applies. Ordinary unconfigured/development builds are exempt and send no usage analytics. This distribution policy does not amend MIT or certify legal validity in every jurisdiction. Cloud-event deletion verification is still pending. The language chosen on this screen is saved and kept after acceptance.

## Published 0.9.1 behavior (historical, superseded by 0.10.0)

The official 0.9.1 release enabled **optional production usage analytics after explicit user consent**. Ordinary development/fork builds remain unconfigured. On 21 October 2026 the owner explicitly authorized launch while deferring end-to-end verification of completed cloud-event deletion. That verification is still pending and is disclosed before consent; it must not be reported as passed. Prior QA verified ingestion, stable event UUID retries and replay-safe counters. Provider deduplication may be delayed; queries deduplicate UUIDs before summing. No RASED scheduled expiry is configured; provider policies and applicable legal requirements still apply.

## User controls and data

The acceptance screen, and later Settings → Privacy & analytics, explains the data before an explicit **Agree & use RASED** action. In the official configured build, not accepting means exiting; development/unconfigured builds have no such requirement. Reference copying, private WhatsApp contact and local forgetting stay available on the acceptance screen. No installation reference is generated before consent. Stopping cancels pending transport and clears queued events; the reference remains available for a deletion request. Forgetting it locally also stops sharing but does not delete previously sent server data.

The disclosure is now `2026-10-21-v4`, including the required-acceptance policy and the pending deletion-verification notice. An earlier opt-in to any former disclosure (including 0.9.1's `2026-10-21-v3`) becomes unknown until the user explicitly accepts again. The existing reference is preserved so previously sent data can still be located. This policy choice does not certify legal compliance or waive statutory rights.

An earlier explicit decline remains disabled when a disclosure changes. Local forgetting first disables sharing and persists an identity-free `purgePending` marker. A dedicated cleanup worker starts only after the sender has exited, enables SQLite secure deletion, clears all queue metadata, vacuums and checks both the checkpoint result and WAL size. Failure stays visible with a keyboard-accessible retry action even without a reference, and blocks enrollment until cleanup completes. Pending cleanup resumes at startup. Only application-owned consent temporary files are removed. This verifies current application files; it does not erase OS backups, snapshots or previously sent cloud records.

Allowed fields are declared and validated in `src/shared/telemetry.ts`: random installation reference, version, language, broad Windows family, qualified daily activity, hourly source/notification counters and selected workflow outcomes. There is no autocapture, replay, screen recording, raw exception upload, project content/URL/ID, proposal text, note, search, custom model ID, AI key or browser identity. Server clocks and client clocks can differ.

PostHog US Cloud is the intended destination. GeoIP is suppressed and the project must discard client IPs. Network infrastructure still receives connecting IP addresses. A build without analytics configuration, development, isolated tests and ordinary forks do not send production events.

For deletion, copy the reference in Settings, stop sharing and contact the developer privately on [WhatsApp](https://wa.me/201201780258). The app does not prefill or transmit the reference to WhatsApp. The administrator verifies the matching installation, requests person/event deletion and checks asynchronous completion before reporting success. After completion, forget the old local reference before enrolling again; do not reuse a deleted distinct ID. Never put references in public GitHub issues.

## Measurement definitions

| Metric | Definition and limits |
| --- | --- |
| Daily / weekly / monthly active | UTC calendar days: today is partial; yesterday and the previous 7/30 complete days exclude today. Distinct participating references, not all users or known people. |
| Interface activity | Focused interaction or an explicit workflow; opening a hidden process alone is insufficient. |
| Monitoring activity | A newly successful source check, excluding cached startup health. |
| First observed | Analytics enrollment, not a verified download or installation. |
| Version adoption | Observed execution; downloading an update does not prove installation. |
| Monitoring hours | Distinct installation/hour pairs containing successful checks, not exact uptime. |
| Notification shown | OS delivery acknowledgement, not proof a person read it. Test notifications are excluded. |
| Quick Apply success | Ready for manual review; never proof of submission. |
| GitHub downloads | Cumulative installer asset counters; repeats and updater full downloads may count. Source archives and blockmaps are excluded. |

Four private dashboards are provisioned by `scripts/analytics/dashboards.mjs`: Overview, Releases & Downloads, Monitoring Health, and Workflows. Every production application query excludes QA and distribution records. Before summing workflow or hourly counters, queries group by event UUID and select one payload, so replayed rows do not inflate `event_count` or source counters. Daily active counts use distinct references. GitHub growth compares consecutive observed asset counts: a gap spans several days and a first observation has no historical delta. Reinstallation/forgetting can create another reference; nonparticipants are unobservable.

Quick Apply keeps the historical `failed` outcome for compatibility, but distinguishes `needs_input`, `login_required`, `draft_exists` and `expired` before classifying general errors. These categories are permitted only on Quick Apply events; they are intentional stops, not evidence of a technical defect. All 19 cards in both the existing production and QA dashboards were validated, updated and read back on 20 October. HogQL requires `toDate(toTimeZone(value, 'UTC'))`, a three-argument `dateDiff`, and timezone conversion before `toStartOfHour`. Literal boundary tests included the first day's 00:05 and excluded today's partial day from complete-day windows.

## Architecture and resilience

The main process owns consent and the UUID. Restricted preload operations expose consent, status, support actions and qualified UI activity; they do not expose arbitrary event capture. A separate worker owns `telemetry/queue.sqlite`, batches up to 50 envelopes / 60 KiB, and never blocks collectors or notifications on network delivery. The project database schema is unchanged.

Queued payloads are bounded to 1,000 records / 2 MiB and seven days. These are logical payload limits, not the physical SQLite file size. Hourly summaries and heavy-use buckets preserve counts; a close/reopen within an hour may produce partial summaries. Distinct installation/hour queries avoid counting these as extra monitoring hours. Retry keeps event UUIDs, honors Retry-After across ordinary restarts and upgrades, and uses bounded backoff. Withdrawal aborts in-flight sending; bytes already accepted by the server cannot be recalled locally. Worker recovery is bounded. Analytics outages do not disable application workflows.

Transport distinguishes authentication (401/403), suspected invalid events (400/422), oversized batches (413), quota-limited acknowledgements and transient errors. Authentication rechecks after 1/2/4 days up to a 7-day wait, or once after an app/schema upgrade; this never resets the separate provider cooldown. Local sleep/withdrawal/close cancellation does not increase or reset network failure counts. Timeouts and HTTP failures do. Successful acknowledgement timestamps remain available across upgrades.

Invalid batches are split left first with at most 12 HTTP requests per send cycle. Accepted parts are acknowledged immediately. Bounded split tasks persist across restarts so an all-invalid prefix cannot repeatedly starve later healthy events. A rejected singleton is dropped only after another part was accepted in that same cycle, up to 20 such drops per UTC day across restarts. Universal rejection drops nothing and backs off. Oversized batches reduce their byte limit; a rejected singleton follows the same guarded isolation policy. Queue age/size eviction still applies independently.

Backups and settings export use explicit app-data allowlists and exclude consent, references and the queue. Restore clears queued telemetry before recording new post-restore activity. No migration adds telemetry to `rased.db`.

## Maintainer operations

Administrative scripts are not bundled into Electron. Keep private keys in environment variables or approved encrypted secrets; never in the renderer, repository, command arguments or logs. The ingest token is write-only and extractable from a distributed client; it is not an administrative secret or an anti-abuse guarantee.

- `node scripts/analytics/admin.mjs dashboards --apply`: validate and reconcile private dashboards using a temporary project-scoped key with dashboard/insight write and query read permissions. Existing owned cards are updated instead of silently retaining obsolete SQL. Ambiguous or shared dashboards are rejected; unrelated cards and layouts are preserved. `--environment=qa` uses separately named QA dashboards and QA-only filters.

Both dashboard entry points check project details before any query or dashboard write: production must be project 670811, while QA requires an explicitly selected, matching project other than production. The local form has no default project. Provisioning now needs project-read permission in addition to its dashboard/query permissions.
- `node scripts/analytics/admin.mjs delete-reference --person=<reviewed-person-uuid> --reference=<installation-reference>`: read-only preview for an authenticated private request. It fetches the profile again and requires exactly the requested installation reference. Missing, mismatched or merged profiles require manual investigation. The reference and person ID differ; do not substitute one for the other.
- Add `--apply` to that reviewed command only after confirming the request and target. It requests deletion of the person and associated events/recordings, and reports pending rather than completed. Use an ephemeral project-scoped `person:write` key with its required read access, never a client ingest token or the retired batch-deletion key.
- `node scripts/analytics/admin.mjs deletion-status --person=<reviewed-person-uuid> --since=<requestedAt>`: check the normal person-deletion status endpoint with `person:read`, using the `requestedAt` timestamp returned by the delete command. A missing or older status row is unknown; only a matching provider verification timestamp can establish reported completion. A server/client clock discrepancy may require manual review. Do not tell the requester it is erased merely because DELETE returned HTTP 202.
- `node scripts/analytics/github-downloads.mjs`: read public release counters; `--apply` sends only aggregate distribution records using the reviewed production ingest token. The project/token fingerprint must match before any request. Daily growth omits each asset's first observed day, including a newly replaced asset; it never treats that unknown delta as zero.
- `node scripts/analytics/local-setup.mjs`: optional 30-minute loopback form for a temporary key transfer without persisting it. Restricts Host/Origin and form nonce; no remote listener. Explicit cloud QA sends synthetic events only to a separate, token-verified QA project. It tests the actual built worker, a lost ingestion acknowledgement, stable UUID retries, exact queryable counters and person creation. The 50-event capture-only option needs no administrative key and accepts only the reviewed QA project/token fingerprint. It explicitly reports cloud querying and deletion as unverified; those checks must be completed separately. QA download testing sends public GitHub totals as separate distribution records. Synthetic deletion is a separate, reviewed operation with an exact target and explicit confirmation; never run it against records the owner has asked to retain. This utility is never started by the app or CI.

The optional GitHub Actions workflow is gated by `RASED_ANALYTICS_OPERATIONS_READY=true`. Its only scheduled operation captures public GitHub download counters using `RASED_POSTHOG_PROJECT_TOKEN`; it has no administrative key and performs no deletion. The previous retention job and `retention` CLI command have been removed. Any existing `RASED_POSTHOG_RETENTION_TOKEN` secret is unused by the current code/workflow; it has not been deleted or repurposed. The reviewed ingest secret is stored in GitHub; scheduled public-download capture is enabled separately during the authorized 0.9.1 launch. The exact future workflow command was run locally and its public distribution records verified in production, without application events. The public-download workflow uses only aggregate public release counters and must be verified independently of application events. Scheduling on GitHub can be delayed or disabled after inactivity; monitor failures and successful runs.

The loopback form also exposes preflight-only operations: stage the reviewed production ingest secret (disable the job first, then pass the token to `gh secret set` on stdin), run the public-download command, and build a configured QA directory package. These operations need no administrative key. `scripts/analytics/preflight.mjs` keeps tokens out of command arguments and error output, does not publish, and restores ordinary unconfigured build output after QA packaging. The manually dispatched `release-build.yml` builds on main using the pre-existing ingest secret only in the build step, verifies the compiled production destination and development/test isolation, runs synthetic/packaged checks and uploads artifacts without publishing. `verify-package.mjs` records only public fingerprints and artifact digests; no administrative key enters the installer. Generated logs and packages belong in ignored `.local/`, not public documentation or release assets.

For an authorized analytics-enabled release, preserve the isolated cloud QA/query evidence and the disclosed pending deletion-verification limitation, then supply `RASED_ANALYTICS_BUILD_TOKEN` and `RASED_ANALYTICS_BUILD_READY=true` at build time. Verify any separately deployed public-download job too. `RASED_ANALYTICS_BUILD_ENVIRONMENT=qa` is for a separately configured QA project; production is the default environment. The unavailable alpha query-based deletion API is no longer a prerequisite because no age-based deletion is performed. These flags are configuration controls, not evidence that cloud-event deletion has completed. Never enable them in isolated automated tests or ordinary fork builds. Current SQL cards have explicit fixed time windows; do not assume dashboard date overrides or global property filters rewrite their SQL.

The guard executes inside `electron.vite.config.ts`, including direct `electron-vite build` invocations. Configured builds require an owner-reviewed token hash in the environment-specific allowlist and either `CI=true` or explicit `RASED_ANALYTICS_LOCAL_RELEASE=true`. Both reviewed destination fingerprints are approved. Production approval follows the owner’s 21 October launch decision and does not certify deletion completion. Fingerprints contain no token values or administrative credentials. Flags alone cannot enable collection. Unconfigured builds strip the token entirely. GitHub actions are pinned to reviewed commit SHAs; automated tests use synthetic runners and do not change settings or secrets.

## Verification

Run `npm run build` before `npm run test:telemetry`. It exercises the built worker with synthetic transport (revocation, generations, retry, permanent failure, restart and sleep), then real Electron/preload/SQLite/UI with marked TEMP profiles. It also checks repeated failed update downloads followed by success: each attempt contributes one terminal outcome, while progress callbacks do not multiply it. Vitest covers runtime allowlists, failed consent-write recovery, transactional daily markers, queue bounds, damaged active buckets, transport acknowledgements, dashboard reconciliation, cloud destination guards and download filtering.

The lifecycle suite also drives an actual collector through success/failure/success, records an isolated project notification, checks graceful hourly sealing and stages an actual backup restore. The Quick Apply suite proves its phase classification through the broker/main/preload/built-worker path. Fixture receivers are outside the app-owned `telemetry/` directory. Tests simulate delivery and do not prove real OS display or foreground behavior. Sanitized startup failures retain only timestamp, startup stage and SQLite code in a rotating 20-entry local log.

`npm run test:startup` holds a real Windows WAL shared-memory mapping after a crashed synthetic writer. It verifies that a bounded startup retry preserves committed records, and that an unrecoverable target error is reported before a clean quit. No database sidecars are manually deleted. This is separate from telemetry delivery: analytics failures remain isolated in their worker.

The live QA project has its own free organization, disabled autocapture/replay and discard-IP enabled. Application records were checked against known counters, including a single active installation despite two activity kinds. Public GitHub snapshots were independently observed in its release dashboard. Four production dashboards were reconciled without sending production application events. A configured QA ASAR passed the Electron consent/worker, lifecycle/restore, native-WAL startup and native-binding checks. A separate QA-branded copy, isolated only for executable identity, OS registration, TEMP storage and disabled platform polling, exercised the regular sender without fixture transport: four startup/enrollment/activity events became queryable only after consent, the natural batch timer delivered them, revocation prevented further sending across another timer interval, and local forgetting completed. Its cloud records had no IP/GeoIP or private-content fields. A real Windows toast click in that copy was separately confirmed by the maintainer and the application's accepted-launch/confirmed-foreground diagnostic. That check is not a claim about every browser or OS configuration. HTTP acknowledgement alone is not used as proof of queryable capture or completed deletion.
